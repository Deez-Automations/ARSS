## Abstract

Security Operations Centers (SOCs) receive thousands of alerts daily from network monitoring tools, and the majority of these alerts are either false positives or low-priority events that do not require immediate attention. The burden of reviewing each alert manually has led to a well-documented problem known as alert fatigue, where analysts become overwhelmed, begin ignoring alerts, and eventually miss genuine threats. Industry data shows that on average, SOC teams receive 4,484 alerts per day, with 67% of those alerts going uninvestigated due to sheer volume [1].

Existing solutions address the detection and aggregation layers of this problem but leave the triage decision to the human analyst. Rule-based automation tools can handle known patterns but cannot adapt to new attack types. Machine learning scoring systems can rank alerts by risk level but do not take response actions and do not explain their decisions in a way analysts can verify or trust.

ARSS (Autonomous Response System for SOC) addresses the triage layer directly. The system intercepts the alert stream after the SIEM and uses a reinforcement learning agent to take one of four triage actions: Ignore, Log, Block, or Isolate. The agent's reward function is grounded in MITRE ATT&CK threat severity weights, which means its policy is aligned with how the security community actually classifies threat seriousness, rather than abstract mathematical costs invented for the training environment. Every automated decision the system makes is accompanied by a plain-English incident narrative, generated by a language model using SHAP feature explanations from the detector and the reasoning behind the RL decision. The goal is to reduce the alert volume that reaches the analyst while maintaining strong threat containment, and to ensure the analyst can understand and verify every action the system took.

## 1. Introduction

The volume of security alerts generated by modern network infrastructure has grown well beyond what human analyst teams can realistically process. Intrusion Detection Systems, firewalls, and SIEM platforms are capable of flagging suspicious activity at scale, but the decision of what to do with each flagged alert still requires a human judgment call in the vast majority of SOC environments. This is the triage problem, and it is where most security operations teams are struggling.

The tools that exist today handle detection and aggregation well. Snort and Suricata identify suspicious sequences. SIEM platforms like Splunk and Microsoft Sentinel collect and score everything. SOAR platforms like Palo Alto XSOAR can automate responses for known attack patterns using pre-written playbooks. But none of these tools learn. When a playbook fires incorrectly and an analyst overrides it, that correction is not fed back into the system. When a new attack type appears, playbooks need to be updated manually. The system has no mechanism to improve its triage decisions over time.

ARSS is built to sit at the SIEM output layer and make triage decisions using a reinforcement learning agent that does learn from outcomes. The agent sees the attack type, the detection confidence, and the danger score, and chooses a response from a four-action space: Ignore the alert, Log it for the analyst to review later, Block the source, or Isolate the affected host. The reward function used to train this agent is derived from MITRE ATT&CK severity classifications, so the agent learns through experience that failing to respond to a Lateral Movement or Credential Access attack is far more costly than missing a Reconnaissance scan.

Beyond the decision itself, ARSS generates a plain-English explanation for every action it takes. This explanation is produced by a language model that reads the top contributing features from the SHAP analysis of the detector alongside the RL agent's triage decision, and turns them into a short narrative that any SOC analyst can read and verify. This explanation layer is not cosmetic. It is the mechanism through which the system builds analyst trust, which is the reason autonomous triage systems tend to fail in practice even when their accuracy metrics are acceptable.

## 2. Problem Statement

SOC analysts at medium and large organizations routinely handle thousands of alerts per day. A 2025 systematic review published in ACM Computing Surveys found that the average SOC team receives 4,484 alerts daily, and that 67% of those alerts go uninvestigated because analysts simply do not have the time to review them all [1]. This is not a failure of detection tools. The alerts are being generated correctly. The failure is at the triage layer, where someone or something needs to decide what to do with each alert before it reaches the analyst.

Current triage approaches have clear limitations. Rule-based SOAR playbooks are static: they handle the attack patterns their authors anticipated and fail on anything new. They also provide no explanation for their decisions beyond "rule X matched," which gives analysts little basis for trusting or auditing the automation. ML-based risk scoring systems rank alerts but do not take response actions, leaving the actual triage decision with the analyst regardless of how well the scoring performs. And critically, none of these systems use feedback from analyst corrections to improve their future decisions.

Academic research in reinforcement learning for alert triage shows that RL is a viable direction, but the existing published work has a consistent limitation: reward functions are grounded in abstract, game-theoretic attack costs rather than real-world threat intelligence frameworks [2][3]. An agent trained to minimize an abstract "defender loss" does not reflect how a real SOC analyst thinks about threat severity. A Reconnaissance scan and a Credential Access attack may receive similar abstract penalties in existing RL systems, even though any experienced analyst would treat them very differently.

The result is a gap between what existing tools offer and what SOC analysts actually need: an adaptive triage system that makes defensible decisions, grounds those decisions in threat intelligence that the security community already uses and trusts, and can explain what it did and why in language an analyst can read in under thirty seconds.

## 3. Problem Solution / Objectives of the Proposed System

ARSS addresses the alert triage gap through three integrated components.

The first is a two-stage detection ensemble. Stage 1 uses an XGBoost classifier and a Deep Neural Network in a soft-voting ensemble to determine whether an incoming network flow represents an attack or benign traffic. Stage 2 takes confirmed attacks and categorizes them into one of seven attack types, again using an ensemble approach, and produces a confidence score alongside the category label. These two stages are trained on the CIC-IIoT 2025 dataset and serve as training infrastructure for the RL agent. In a live deployment, the SIEM already provides equivalent scoring and labeling, so these stages are replaced by the SIEM output directly.

The second component is the RL triage agent. This is a Deep Q-Network (DQN) that receives a state vector composed of the danger score, the attack category as a one-hot encoding across seven classes, and the classification confidence. It outputs one of four triage actions: Ignore, Log, Block, or Isolate. The reward function is built around MITRE ATT&CK severity weights, assigning severity scores to each attack category based on the tactic the attack maps to in the MITRE framework. MITM attacks map to Credential Access and Collection tactics and carry a severity weight of 1.0. Reconnaissance scans map to the Discovery tactic and carry a weight of 0.3. The agent learns through training that the penalty for missing a high-severity attack scales with that attack's MITRE weight, which produces a policy that reflects real threat prioritization rather than abstract game costs.

The third component is the Cognitive Semantic Layer. After the RL agent makes a triage decision, a language model (Gemini) receives both the SHAP feature attributions from the Stage 2 detector and the RL decision, and generates a short plain-English incident narrative. This narrative is shown on the SOC dashboard alongside the triage action, giving the analyst a human-readable explanation of what was detected, which network features drove the classification, and why the agent responded the way it did. This layer is what separates ARSS from a black-box automation tool and is central to the system's goal of building analyst trust.

### 3.1 Objectives

**BO-1:** Train a two-stage ML ensemble (XGBoost + DNN) on the CIC-IIoT 2025 dataset that achieves high recall in binary attack detection (Stage 1) and reliable multi-class categorization across seven attack types with confidence scoring (Stage 2).

**BO-2:** Design a category-conditioned state space for the RL agent that encodes attack semantics (category + confidence) alongside danger score, enabling the agent to learn distinct response policies for different attack types at the same risk level.

**BO-3:** Train a DQN agent using a MITRE ATT&CK severity-weighted reward function that explicitly penalizes missed high-severity threats proportionally to their MITRE tactic classification, optimizing the tradeoff between analyst workload reduction and threat containment.

**BO-4:** Implement a Cognitive Semantic Layer using a language model that combines SHAP feature attributions from the detector with the RL triage decision to produce plain-English incident narratives for the SOC analyst dashboard.

**BO-5:** Demonstrate, through baseline comparison, that the category-conditioned RL agent outperforms a rule-based threshold system on threat containment rate while reducing the proportion of alerts escalated to human analysts.

**BO-6:** Evaluate the full end-to-end pipeline on the CIC-IIoT 2025 dataset and report the proportion of alerts handled autonomously, the false negative rate by attack category, and the false positive escalation rate to analysts.

## 5. Vision Statement

For SOC teams and security operations managers dealing with alert volumes that exceed what any human team can realistically process, ARSS is an autonomous triage agent that handles routine alerts automatically, escalates genuine threats with full explanations attached, and learns to improve its decisions over time. Unlike static SOAR playbooks that break on new attack types, and unlike existing RL research that trains on abstract costs disconnected from real threat intelligence, ARSS grounds every triage decision in the MITRE ATT&CK framework that the security community already uses, and explains every decision in plain English that any analyst can read and verify. The system is not designed to replace the SOC analyst. It is designed to protect the analyst's attention so that when a genuine, high-severity threat arrives, the analyst has the capacity and the context to respond to it effectively.

## 6. Scope

ARSS is a triage layer designed to sit downstream of a SIEM system. The system receives alert data that has already been scored and labeled by upstream detection tools, processes it through a trained RL policy, and returns a triage decision along with a plain-English explanation. The project covers the following components within its scope.

**Two-Stage Detection Ensemble.** A binary classifier (Stage 1) and a 7-class attack categorizer (Stage 2), each implemented as an ensemble of XGBoost and a Deep Neural Network. These are trained on the CIC-IIoT 2025 dataset. In the training phase, these stages enrich raw network flow data into the state vector the RL agent requires. In production deployment, these stages are not needed because the SIEM provides equivalent data. The trained RL policy is the deliverable, not the detection pipeline.

**DQN Triage Agent.** A Deep Q-Network trained with a MITRE ATT&CK severity-weighted reward function. State space: danger score (continuous), attack category (one-hot across 7 classes), classification confidence (continuous). Action space: Ignore, Log, Block, Isolate. Reward function: correct handling of a true attack yields a reward scaled by the MITRE severity weight of that attack category. Missing a true attack incurs a penalty scaled by that same weight. Escalating a false positive to the analyst incurs a fixed penalty reflecting wasted analyst time. The LOG action represents human deferral and is rewarded when the system correctly identifies that a case needs human judgment.

**SHAP Explainability Layer.** Applied to the Stage 2 detector output. Produces the top 5 contributing network features for each classification decision. These attributions are passed to the Cognitive Semantic Layer.

**Cognitive Semantic Layer.** A Gemini language model integration that receives the SHAP attributions from the detector and the RL agent's triage decision, and generates a short plain-English incident narrative for display on the SOC dashboard. The narrative describes what was detected, which features were most significant, and why the chosen response action was appropriate given the threat type.

**SOC Dashboard.** A simple web interface displaying the live alert stream, the triage decision for each alert, the confidence score, the attack category, and the analyst-readable explanation. Analysts can override decisions and review anything flagged as LOG.

**Out of Scope for Initial Prototype.** Real-time packet capture, IDS or IPS functionality, and live SIEM integration are not part of the initial prototype. The system will be evaluated using pre-recorded CIC-IIoT 2025 data with simulated alert replay. Live SIEM API integration is planned for the later implementation phase.
